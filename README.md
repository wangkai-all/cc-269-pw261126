# 发布控制台 · 本地数据产品

一个不依赖任何真实消息中间件的发布演示：一个发布器、三个可独立启停的本地消费者、
一个网页控制台，完整走通 **发布 → 确认 → 拒绝 → 回退 / 撤销 → 恢复** 一轮。

核心约束：**已发送 ≠ 已生效**。控制台记录每个下游“究竟确认了哪个版本”，
发布器自己的投递动作永远不算送达。

```
浏览器 ──► 发布器 :4601 ──HTTP──► alpha :4611
              │      └──HTTP──► beta  :4612
              │      └──HTTP──► gamma :4613
              └ 进程管理器 :4600（start/stop/restart/crash 三个独立进程）
```

## 快速开始

```bash
npm start            # 启动发布器 + 三个消费者（各自独立进程）
# 打开 http://127.0.0.1:4601
```

停止：`Ctrl+C`（会逐个优雅关闭）。清空演示数据：`npm run reset`。

也可以完全手动启停，不通过进程管理器：

```bash
npm run start:direct                                   # 发布器
npm run consumer -- --name alpha                       # 终端 1
npm run consumer -- --name beta                        # 终端 2
npm run consumer -- --name gamma                       # 终端 3
```

消费者支持 `--port`、`--data`、`--schema`、`--publisher` 参数，默认端口
alpha=4611 / beta=4612 / gamma=4613，数据在 `.data/<name>/`。

## 一轮演示脚本（5 分钟）

1. **发布 v1**：输入 `v1`，schema `v1`，点“新建草稿” → “发布并投递”。
   观察每个下游先显示“已发送·待确认”，约 1 秒后变为“已确认生效”。
   确认 3/3 后点“切为正式版”。
2. **制造不兼容**：新建 `v2`，schema 选 `v2`，发布。
   alpha / beta 确认，gamma 显示“结构性拒绝：unsupported schema v2”。
   此时“全员一致”策略下切版按钮不可用，并列出阻塞原因。
3. **看策略差异**：把右上角策略切到“法定人数 + 允许落后”，保存，
   再切 v2。gamma 保留在 v1，并得到落后截止时间。页面同时显示兼容窗口。
4. **回退**：对 v2 点“回退”。系统不是把下游版本改回 v1，而是**向前发布**
   `v1-restore-N`，三个下游依次确认后自动切为正式版。
5. **紧急撤销**：新建 v3 并发布，等 alpha/beta 确认（gamma 仍拒绝）。
   停掉 beta，再点“紧急撤销”。
   - alpha（已消费）→ 隔离，数据保留但不再对外提供；
   - beta（离线）→ 撤销处于“待确认”，发布器每轮重试；
   - gamma（未消费）→ 拉黑。
   启动 beta，几秒内它回执“未消费”，撤销全部核对完成。
6. **确认幂等**：任一已确认版本上点“重放一条确认” → 被识别为 `duplicate`，
   有效版本不变；点“注入迟到确认” → 被判定 `stale`。
7. **崩溃恢复**：点“重启发布进程”（SIGKILL 后重启）。事件日志重放，
   正式版、确认计数、重复/迟到计数全部保持不变。

每个下游卡片上还有“停止 / 重启 / 崩溃 / 本地状态”，可以演示长时间离线的下游
在恢复后从磁盘日志接上，而且**不会重复应用**已经应用过的版本。

## 策略与语义

详细论证见 [docs/RELEASE_POLICY.md](docs/RELEASE_POLICY.md)。结论：

- **全员一致后切版**（默认）：等待窗口 15 分钟内三个下游全部确认才切版；
  结构性拒绝直接阻塞；窗口到期只提醒，不自动切版。
- **法定人数 + 允许落后**：2/3 确认即可切版，未确认者获得落后截止时间；
  不兼容下游在兼容窗口（默认 24h，从新 schema 首次发布起算）内可暂不升级，
  窗口过期需要显式业务例外。
- **撤销**：已消费 → 隔离；未消费 → 拉黑。撤销后任何确认都不能把它翻回“已生效”。
- **回退**：向前发布上一版本内容的新版本，下游版本号永不倒退。

## 状态机保证

| 场景 | 行为 |
| --- | --- |
| 重复确认 | 回 `duplicate: true`，只加审计计数，不重复应用 |
| 旧确认迟到 | 按 `dispatchSeq` 判定 `stale`，不改变任何状态；重启后判定一致 |
| 发布进程崩溃 | 启动时重放事件日志；尾部半条记录截断，中段损坏拒绝启动 |
| 下游崩溃/离线 | 投递超时记为 `timeout`（不算送达）；恢复后按需重投，幂等 |
| 撤销时下游离线 | 撤销结果保持待确认，每轮扫描重试直到回执 |

## 代码结构

```
src/shared/journal.js     append-only JSONL 事件日志（fdatasync、撕裂修复、重放）
src/shared/schema.js      数据产品载荷、校验、schema 兼容判定
src/publisher/store.js    发布器状态机（纯 reducer，重放即可重建）
src/publisher/server.js   发布器 HTTP：控制 API + 投递/确认总线 + 静态页面
src/consumer/store.js     消费者副本（幂等应用、确认 outbox、隔离/拉黑）
src/consumer/agent.js     消费者进程（独立端口、独立数据目录）
scripts/supervise.js      本地进程管理器（start/stop/restart/crash）
public/                   网页控制台（无构建步骤，原生 ES 模块）
tests/                    node:test 集成测试
```
